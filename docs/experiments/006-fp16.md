# FP16 storage with Float32 arithmetic

## Problem

Float32-only execution cannot exercise reduced storage precision or its accuracy/performance tradeoffs.

## Hypothesis

FP16 storage may reduce logical payload traffic, but conversion costs and Float32 scalar arithmetic mean a speedup is not guaranteed.

## Baseline

Existing Float32 naive/tiled operators and separately measured same-dtype fusion pairs. Use equivalent shapes and explicit quantized-input references when comparing precision.

## Implementation

FP16 loads/stores, Float32 GEMM accumulation and Softmax reductions, optional fused GEMM-ReLU. No Tensor Core instructions. Softmax avoids intermediate half rounding of exponentials.

## Benchmark methodology

Run fp16_cuda correctness checks first. Use forge_fp16_compare and forge_fp16_fusion_compare for the same recorded shape/warmup/sample settings as Float32 runs. Full double-precision reference uses decoded FP16 operands; expected output is rounded to FP16. GEMM benchmarks allow 0.002 absolute plus 0.002 relative error. Metadata identifies precision and arithmetic, and timing excludes transfers/reference/allocations. CUDA-event intervals can include submission gaps. Capture commit, hardware, toolchain and repeated runs before drawing conclusions.

## Results

Host metadata/dispatch validation passed. GPU numerical checks: NOT YET RUN. Performance: NOT YET MEASURED.

## Interpretation

Half-sized payloads do not establish half the measured memory consumption or faster execution. Padding, conversion, kernel structure and launch overhead matter. FP16 output range and rounding differ from Float32 even with Float32 accumulation.

## Conclusion

FP16 candidate execution is implemented, with Tensor Cores explicitly absent. Validate numerical tolerances and benchmark on NVIDIA hardware before accepting performance claims.
